# Extension Permissions sought and store submission (why not!)

This note explains why ExtScanAlert asks for certain extension permissions, what those permissions are used for in practice, and why the project currently makes more sense as a manual-install extension than a Chrome Web Store release.[cite:1380][cite:1381]

## Why this note exists

ExtScanAlert is designed as a user-controlled privacy and auditing tool. It inspects technical signals such as extension-probe attempts, vendor-linked fingerprinting activity, site-specific rules, and optional blocking behavior. Because of that, it needs permissions that can look broad at first glance, especially scripting, request handling, and host access.[cite:1380]

At the same time, the extension is still intended to be edited by advanced users who want to tune provider behavior and noise reduction for their own browsing style. That manual-edit model is one of the main reasons a normal store submission is not the ideal fit right now.[cite:1380]

## Why store submission is not the best fit right now

The current project is meant to be manually installed and adjusted by the user. In particular, several JSON files are expected to be edited locally so users can adapt the extension to their own preferences, false positives, and blocking style.

The main files that may need manual editing are:

- `providers.json` — defines known vendors, categories, UI notes, score boosts, and how provider-linked events are classified.
- `slow-rules.json` — contains optional rules for blocking known heavy widgets or scripts that can degrade page performance.
- `noise-domains-curated.json` — used to suppress or downgrade known noisy domains that are not useful for the user’s own analysis.

That model is practical for a GitHub-distributed project, but it is awkward for a normal store listing because store users generally expect ready-to-use defaults, minimal manual editing, and settings to be changed through the extension UI rather than by editing packaged files.[cite:1380][cite:1381]

A Chrome Web Store review would also focus heavily on broad permissions and host access. Even if those permissions are justified, the review burden is higher when the extension injects scripts, observes web activity, and uses host permissions across many sites.[cite:1380][cite:1381]

## Permission overview

The table below summarizes the permissions that would typically need justification in a store submission flow.

| Permission | Why it is needed | Practical use in ExtScanAlert |
|---|---|---|
| `storage` | Saves settings and user choices locally. | Stores global mode, notification preference, per-site rules, and locally kept fingerprint logs for review/export. |
| `scripting` | Allows the extension to inject monitoring code into pages. | Used for page-level hooks that observe APIs such as canvas and WebGL when fingerprint-style behavior is being audited. |
| `tabs` | Lets the popup understand the current site context. | Reads the active tab hostname so the popup can show and apply site-specific Allow / Observe / Block rules. |
| `notifications` | Shows block or warning messages to the user. | Supports the “notify once per host when blocked” feature for probe or vendor blocking events. |
| `declarativeNetRequest` | Enforces network-level allow/block rules. | Applies known provider rules and optional protection rules without needing invasive real-time packet inspection. |
| `webRequest` | Observes request activity where additional context is useful. | Can be used to associate known third-party requests with logged activity when DNR alone is not enough for attribution. |
| Host permissions | Lets the extension operate on the pages the user visits. | Required so page hooks and request logic can function across the sites the user actually wants to inspect. |

## Suggested permission justifications

These are the kind of short, plain-language explanations that would normally be given in a store submission form.

### storage

Used to persist local extension settings, per-site rules, notification preferences, and fingerprint-monitor logs generated by the extension. No settings or logs are transmitted to a remote service by default.

### scripting

Used to inject a lightweight page-monitoring script so the extension can observe browser APIs such as canvas and WebGL when auditing fingerprinting-style behavior. This is required for on-page technical detection and local event attribution.

### tabs

Used to identify the active tab’s hostname so the popup can display and apply site-specific rules. This permission supports the current-site controls and does not exist to track general browsing history.

### notifications

Used to show user-visible alerts when the extension blocks a probe or vendor script and the user has enabled notifications. Notifications are functional and local to the extension’s protection features.

### declarativeNetRequest

Used to apply user-controlled block, observe, and protection rules through Chrome’s built-in request filtering model. This supports known provider blocking, optional fingerprint protection, and other user-defined rule behavior.

### webRequest

Used to observe request context for logging and attribution where declarative rules alone do not provide enough detail. This helps associate third-party requests with recorded fingerprint-monitor events.

### Host permissions

Required so the extension can operate on sites visited by the user, including observing fingerprint-related API use and attributing activity to known third-party vendors. The purpose is technical monitoring and user-controlled blocking, not remote collection of page content.

## Why manual JSON editing still matters

The extension is intentionally opinionated but not locked down. Different users will have different tolerance levels for noise, false positives, broken-site risk, and what they consider worth blocking.

Manual editing allows users to:

- add or remove vendors in `providers.json`;
- tune optional performance-related rules in `slow-rules.json`;
- reduce clutter by editing `noise-domains-curated.json`;
- adapt the extension to regional sites, niche providers, or personal browsing habits.

That flexibility is one of the project’s strengths, but it also makes the extension more of a power-user or GitHub-first tool than a polished mass-market store package in its current form.

## Practical takeaway

ExtScanAlert can justify its permissions in a coherent way because each one maps to a visible feature: page-level detection, local logging, site rules, notifications, and optional blocking.[cite:1380]

The bigger reason not to push for store submission right now is not that the permissions are impossible to explain. It is that the project still expects technically confident users to edit core JSON configuration files for their own preferences, which fits manual installation and repository-based distribution far better than a typical one-click store install.[cite:1380][cite:1381]
