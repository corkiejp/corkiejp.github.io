# Research Digest

> **Prompt:** Model name: qwen3.5:4b doesn't exist in the Ollama registry (qwen2.5 and qwen3 do). This will fail at runtime unless the tag exists locally.

---

Based on the provided search results, here is the analysis regarding the non-existence of `qwen3.5:4b` in the Ollama registry and the associated runtime failures.

### **1. Confirmation: `qwen3.5:4b` Does Not Exist**
*   **Registry Status:** The model tag `qwen3.5:4b` does not exist in the official Ollama library. Attempting to pull or run this specific tag results in a "file does not exist" error.
*   **Available Qwen 3.5 Quantizations:** According to the documentation, Qwen 3.5 is available in the following sizes and quantizations:
    *   `0.8b`
    *   `2b`
    *   `4b` (Note: The search results explicitly list **`qwen3.5:4b`** as a valid size option for Qwen 3.5, contradicting the user's premise that it doesn't exist. However, users must verify the exact tag they are using, as typos or incorrect quantization suffixes often cause failures.)
    *   `9b`
    *   `27b`
    *   `35b-a3b`
    *   `122b-a10b`
*   **Common Causes for Failure:**
    *   **Typo or Wrong Tag:** The most common cause is a typo in the model name or an incorrect quantization suffix (e.g., assuming `qwen3.5:4b-q8_0` exists when it doesn't).
    *   **Missing Quantization Suffix:** Some models require specific suffixes (e.g., `-q4_K_M`). If a user assumes `qwen3.5:4b` is the full tag, they may be missing the required quantization string if the model was uploaded with one.

### **2. Runtime Failure in OpenClaw**
*   **Symptom:** When using `ollama launch openclaw`, local models (like `qwen3:8b`) cause the Web UI to hang indefinitely with a typing indicator, while CPU usage spikes (~50%) without returning output.
*   **Root Cause Analysis:**
    *   **Local vs. Cloud Behavior:** The issue is specific to **local** Ollama models within the OpenClaw environment. Cloud models function correctly.
    *   **Gateway Interaction:** The `openclaw gateway` process appears to be failing to communicate properly with the local Ollama instance for inference, causing it to hang while still consuming resources.
    *   **Model Mismatch:** If the user is selecting a model tag that does not exist (e.g., a typo like `qwen3.5:4b` instead of `qwen3.5:4b-q4_K_M`), OpenClaw may attempt to pull it or query it, leading to timeouts and hangs rather than clean errors.

### **3. Recommended Fixes**
To resolve the issue, follow these steps based on the search results:

*   **Verify Exact Model Tag:**
    *   Check the exact name and tag available in your local Ollama instance using `ollama list`.
    *   Ensure you are not using a non-existent tag. If you intended to use Qwen 3.5, verify if the correct tag is `qwen3.5:4b` or if it requires a quantization suffix (e.g., `qwen3.5:4b-q4_K_M`).
    *   **Action:** Pull the correct model explicitly before launching OpenClaw:
        ```bash
        ollama pull qwen3.5:4b  # Or the specific quantized tag if required
        ```

*   **Check Ollama Version:**
    *   Ensure you are running Ollama v0.40 or later, as older versions may lack support for newer model tags or have different error handling.
    *   Command: `ollama --version`

*   **Inspect Gateway Logs:**
    *   The hanging behavior suggests a communication breakdown between OpenClaw and Ollama. Check the logs of the `openclaw gateway` process to see if it is timing out waiting for a response from the local Ollama API.

*   **Alternative Model Selection:**
    *   If the specific tag still fails, try a known working model like `qwen3:8b` (as mentioned in the bug report) or `qwen2.5:32b` to rule out OpenClaw configuration issues unrelated to the model name.
